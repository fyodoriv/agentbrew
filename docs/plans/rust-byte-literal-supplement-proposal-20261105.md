# Supplemental byte-literal registration proposal

Status: proposed, not registered. No supplemental test code, parser/compiler invocation, decoder implementation or product result exists. Initial main-corpus prediction was committed normally as `4b040d8ba6e9a9e8c6835c39252e9cd35d5e00cd` before this document was authored.

## Overall goal and vision

Qualify the intended Syn LitByteStr body form rather than silently narrowing the adapter to string literals. Bind the decoded bytes and exact source/receipt/output through actual discovery and validation. Preserve all original inventory, parser and reviewed-registry acceptance, and all original6P/50N/2C records byte-for-byte. The existing symbolic canary remains preservation only.

## Decision and alternatives

Reuse the already pinned Syn2.0.119 LitByteStr::value and standard strict UTF-8 conversion. Do not add a decoder dependency, handwritten unescaper, lossy conversion, compiler/source execution, runtime selector or native worker. Parser/trace state remains source-analysis scope; facts remain discovery-invocation scope.

The Rust reference distinguishes byte escapes from raw-byte syntax: cooked byte strings can contain arbitrary byte escapes; raw byte literals must contain ASCII source characters. Therefore a valid raw byte token cannot itself yield non-UTF-8 bytes. BS01 is explicitly a lexer/syntax refusal, not a fabricated UTF-8-decoder refusal. Primary reference checked Nov5: [Rust literal tokens](https://doc.rust-lang.org/reference/tokens.html#byte-string-literals). Cached pinned proc-macro2`src/parse.rs:442-509` enforces ASCII byte-token grammar; cached Syn`src/lit.rs:294-297,1412-1487` supplies Vec<u8> literal decoding. No parser was executed to author these expectations.

Each self-description entry is canonical compact sorted-key JSON plusLF and has a null manifest self receipt. Separate denominators:3 accepted byte positives (BP01 cooked ASCII, BP02 raw ASCII, BP03 cooked escaped valid multi-byte UTF-8);3 UTF-8-decoding refusal controls (BN01 invalid leading byte, BN02 incomplete EOF sequence, BN03 invalid continuation);1 raw-byte grammar refusal (BS01). Do not fold these into the original six or fifty, or report four decoder refusals.

Every accepted case needs an empty validation diagnostic set and exact real call/body/output witnesses and required edges. The byte-token span includes b or br prefix and delimiters. The receipt body is decoded UTF-8 text while the source remains its original escaped/token bytes. BP03 prevents an ASCII-only shortcut from appearing to implement UTF-8.

Every decoding refusal needs a real resolved standard writer, valid parsed byte literal, exact decoded-byte length/content, the stated UTF-8 error offset/length, an Unknown body Datum at the real token span, and both named existing diagnostics. It must not emit a generated-body fact, use U+FFFD replacement or let a registry record override the known decoding contradiction. A generic unsupported Rust diagnostic does not qualify the refusal. The frozen manifest declares only the known program/call/output for these incomplete bodies; it does not invent a UTF-8 program.

BS01 needs the Rust frontend/lexer to reject the non-ASCII raw byte token before decoding. It cannot qualify through a missing parser, wrong setup, generic registry requirement, compiler failure or stale receipt. Trace is cfg(test)-only read-only per-invocation observation, not an authority input or production report change.
